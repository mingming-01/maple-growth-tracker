# Phase 4–6 및 프런트엔드 전환 로드맵

기준 저장소: `mingming-01/maple-growth-tracker`

## 진행 원칙

- Flask API, Nexon API 연동, 데이터 저장소, 성장 계산은 검증 없이 교체하지 않는다.
- 기능 단계와 UI 프레임워크 전환을 분리한다. 기능을 먼저 안정화하고 React 전환은 별도 단계에서 진행한다.
- 수치 계산은 Python/JavaScript 코드에서 수행하고, AI는 계산 결과의 설명과 해석만 담당한다.
- 기록이 없거나 표본이 부족한 경우 0으로 보정하거나 추세를 만들어내지 않는다.
- 각 단계는 별도 브랜치와 PR로 진행하며, 기본 CI와 관련 브라우저 E2E가 통과한 변경만 병합한다.

## Phase 5 — AI 성장 분석 고도화

상태: 진행 중

### 목표

사용자가 7일·30일·90일 중 선택한 기록 범위와 실제 데이터 품질을 AI 분석에 반영한다.

### 코드가 계산하는 분석 지표

- 분석 기간 시작일·종료일과 실제 정상 기록 충실도
- 관측된 경험치 변화 구간 수
- 기간 전반부와 후반부의 관측 평균 비교
- 평일과 주말의 관측 평균 및 주말 양수 성장 비중
- 직전 동일 길이 기간의 관측 평균 대비 변화
- 이전 기간 또는 요일별 표본이 부족한 경우의 분석 불가 상태

### 해석 규칙

- AI에게 경험치·평균·변화율·예상 날짜 계산을 맡기지 않는다.
- 직전 기간 비교는 두 기간 모두 관측 표본이 있을 때만 사용한다.
- 평일·주말 비교는 각 그룹에 최소 2개의 관측 변화 구간이 있을 때만 해석한다.
- 전반부·후반부 추세도 각 구간에 최소 2개의 관측 변화 구간이 있을 때만 해석한다.
- 선택 기간이 7일을 초과하면 최근 7일 기록을 전체 기간 기록과 혼합하지 않는다.
- 다음 레벨업 예상은 기존 화면과 일치하도록 최근 7일 평균 기준을 유지한다.

### 완료 조건

- 7일·30일·90일 선택에 따라 AI 요청의 분석 기간과 계산 지표가 일치한다.
- 직전 기간 자료가 없으면 비교를 생성하지 않는다.
- 미수집·API 미제공·레벨업 경계의 변화량을 임의 추정하지 않는다.
- JavaScript 단위 테스트와 브라우저 E2E에서 요청 payload 및 화면 근거를 검증한다.
- Gemini/OpenRouter 응답이 없을 때의 사용자 안내와 코드 기반 기본 분석 정책을 별도로 검토한다.

## Phase 6 — 개인화 기능

상태: 계획

### 6.1 성장 목표

- 캐릭터별 목표 레벨과 목표 날짜 설정
- 현재 레벨·최근 성장 추세에 따른 목표 달성률 계산
- 목표 달성 가능성은 실제 관측 평균과 데이터 충실도를 함께 표시
- 목표를 수정·삭제할 수 있는 관리 UI
- 초기 버전은 브라우저 저장소에 보관하며, 서버 계정 동기화와 명확히 구분

### 6.2 관심 캐릭터 확장

- 기존 관심 캐릭터 목록을 그대로 재사용
- 관심 캐릭터별 최신 조회 시각과 데이터 상태 표시
- 일괄 조회는 API 호출 제한을 고려한 제한된 동시성·실패 격리 적용
- 캐릭터별 목표 및 최근 성장 요약 연결

### 6.3 알림 및 동기화

- 첫 단계는 사이트 방문 시 확인하는 알림/목표 상태 표시
- 브라우저 푸시 알림은 권한 요청, 서비스 워커, 알림 수신 동작을 별도 검증한 뒤 도입
- 기기 간 동기화는 인증·계정·개인정보 삭제 정책이 준비된 이후 진행
- 인증을 도입하기 전에는 사용자 데이터를 서버의 공용 목록에 저장하지 않는다.

### 완료 조건

- 여러 캐릭터의 목표가 서로 섞이지 않는다.
- 목표 달성률은 코드에서 계산하고 원본 기록과 산식이 확인 가능하다.
- 기록이 부족하면 달성 가능성 대신 자료 부족을 표시한다.
- 저장소를 사용할 수 없어도 기존 캐릭터 조회·성장 분석 기능은 영향을 받지 않는다.

## Phase 7 — React + Vite 프런트엔드 전환

상태: 계획

### 유지할 영역

- Flask 애플리케이션 및 API 엔드포인트
- Nexon Open API 연동과 데이터 수집
- PostgreSQL·SQLite 저장소
- 성장 계산·기간 비교·AI 제공자 연동
- 관리자 화면과 관리자 인증(별도 검토 없이 재작성하지 않음)

### 전환 전략

1. `frontend/` 아래에 React·TypeScript·Vite 앱을 별도로 구성한다.
2. Vite 빌드 산출물을 Flask가 제공할 수 있는 정적 경로로 출력한다.
3. 초기에는 별도 미리보기 경로에서 React 화면을 실행하고 기존 화면을 기본 경로로 유지한다.
4. API 클라이언트를 기존 Flask 응답 계약에 맞추고, 임의의 새 API를 만들지 않는다.
5. 공통 디자인 토큰, 반응형 레이아웃, 검색·성장 요약부터 작은 단위로 이전한다.
6. 그래프·비교·개인화·캐릭터 상세(장비·스탯·프리셋·유니온)를 각각 독립적으로 이전하고 회귀 테스트한다.
7. 기존 화면과 React 화면의 데이터·기능 동등성을 확인한 뒤 기본 경로를 전환한다.
8. 전환 직후에도 기존 화면으로 되돌릴 수 있는 롤백 경로를 일정 기간 유지한다.

### 금지할 위험한 전환

- Flask 백엔드를 React로 대체하지 않는다.
- 기존 기능을 일괄 삭제한 뒤 새 UI를 한 번에 구현하지 않는다.
- Nexon API 호출을 React 브라우저에서 직접 수행하거나 API Key를 프런트엔드에 노출하지 않는다.
- React 전환과 DB 스키마 개편·인증 시스템 도입을 한 PR에 묶지 않는다.

### 완료 조건

- 기존 API 계약과 응답 의미를 유지한다.
- 기존 핵심 기능에 대한 회귀 E2E가 통과한다.
- 데스크톱·태블릿·모바일 레이아웃이 검증된다.
- 빌드 산출물과 Render 배포 절차가 재현 가능하다.
- 전환 후 문제가 발생하면 기존 UI로 복귀할 수 있다.
